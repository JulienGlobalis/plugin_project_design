# Project Model Checklist

## Model Boundary

- [ ] The Project View represents normalized project understanding rather
      than source documents or every Knowledge Assertion.
- [ ] Project Elements use the Canonical Domain Model without redefining its
      concepts.
- [ ] Knowledge provenance, confidence, validation, and assertion
      relationships remain in the Knowledge Model.
- [ ] Generated artefacts, skill methodologies, schemas, persistence, and
      runtime behavior remain outside the Project Model.

## Normalized Representation

- [ ] One Project View gives future skills a coherent shared project context.
- [ ] Every Project Element expresses one independently referenceable
      canonical meaning.
- [ ] Project Relationships preserve meaningful connections between elements
      without inventing canonical concepts.
- [ ] Existing, Target, and Transition perspectives remain distinguishable
      when state affects meaning.
- [ ] Current Project View currency is not confused with Existing lifecycle
      perspective.

## Resolution and Uncertainty

- [ ] Established information has reviewed, applicable, and sufficiently
      authoritative knowledge or an authorized Decision as support.
- [ ] Provisional information has an explicit working basis and retains its
      conditions.
- [ ] Unresolved information preserves material gaps or alternatives without
      selecting an unsupported winner.
- [ ] Normalization Status remains distinct from Knowledge validation,
      confidence, and source authority.
- [ ] Unresolved status remains distinct from the canonical Open Question
      concept.
- [ ] Missing concepts are not automatically treated as known absent, not
      applicable, or unresolved.
- [ ] Rejected and superseded assertions remain Knowledge Model concerns.

## Knowledge Consumption and Traceability

- [ ] Every material Project Element and Project Relationship has a Knowledge
      Basis.
- [ ] Supporting, Qualifying, and Opposing evidence roles remain distinct.
- [ ] Material opposing knowledge remains linked after an authorized
      resolution.
- [ ] The derivation mapping supports Project Model to Knowledge Model and
      Knowledge Model to Project Model tracing without modifying the
      Knowledge Model.
- [ ] New project information enters through source documents and Knowledge
      Assertions before changing the Project View.

## Skill Consumption

- [ ] All future skills consume the same normalized Project View.
- [ ] Established, Provisional, and Unresolved information have consistent
      consumption semantics across skills.
- [ ] Skills may select relevant project information without creating private
      normalized truth.
- [ ] Skill-specific readiness, content, prioritization, and presentation
      rules remain outside the shared model.
- [ ] Completeness is evaluated for a declared purpose rather than stored as a
      universal project status.

## Architecture and Corpus Compatibility

- [ ] The model represents incomplete, contradictory, modernization, new, and
      purpose-complete project states with the same minimal constructions.
- [ ] All four permanent fixtures are representable without unsupported
      normalization.
- [ ] The model remains technology-independent, storage-independent,
      methodology-independent, and platform-independent.
- [ ] Spec Kit remains an optional downstream integration.
- [ ] The Canonical Domain Model file and concepts remain unchanged.
- [ ] The Knowledge Model file and responsibilities remain unchanged.
